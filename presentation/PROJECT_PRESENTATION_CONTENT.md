# Thrashing Mitigator

## ใช้ RAM ที่มีให้คุ้ม ก่อนตัดสินใจอัปเกรด

เนื้อหาสำหรับนำเสนอโครงการในวิชา Operating Systems อ้างอิงแอปรุ่นปัจจุบัน ณ วันที่ 13 ตุลาคม 2026 และเอกสารเรียนที่ผู้จัดทำให้มา เนื้อหาแบ่งตามประเด็นเพื่อให้นำไปจัดสไลด์ได้โดยไม่ผูกกับจำนวนหน้า

## 1. บทคัดย่อโครงการ

Thrashing Mitigator เป็นแอปพลิเคชันบน Windows ที่ช่วยให้ผู้ใช้ติดตามการใช้หน่วยความจำของเครื่อง วิเคราะห์การเปลี่ยนแปลงของ RAM รายแอป และเรียกใช้กลไกของ Windows เพื่อคืนหน่วยความจำบางส่วนกลับมาใช้งาน แอปประกอบด้วยหน้า Overview สำหรับข้อมูลสด หน้า Auto สำหรับกำหนดเงื่อนไข Optimize อัตโนมัติ หน้า Insights สำหรับดูประวัติย้อนหลัง และหน้า Settings สำหรับการตั้งค่าการใช้งาน

โครงการนำแนวคิดเรื่อง Main Memory, Process, Paging และ Swapping มาประยุกต์กับข้อมูลที่วัดได้บนระบบปฏิบัติการจริง ผู้ใช้สามารถตรวจว่าหน่วยความจำพร้อมใช้งานเปลี่ยนแปลงเท่าใดหลัง Optimize รวมถึงดูขั้นตอนที่ทำสำเร็จ ขั้นตอนที่ข้าม และข้อจำกัดด้านสิทธิ์

คุณค่าของโครงการอยู่ที่การทำให้ผู้ใช้เห็นสถานะและผลของการจัดการหน่วยความจำได้ชัดขึ้น ผลการคืน RAM ขึ้นอยู่กับโปรเซส ภาระงาน และสิทธิ์ที่มี การเพิ่มความจุ RAM ทางกายภาพยังต้องอาศัยฮาร์ดแวร์ ส่วนการยืนยันผลด้านความเร็วและการลด Thrashing ต้องมีการทดลองเพิ่มเติม

## 2. ที่มาและความสำคัญของปัญหา

### 2.1 การใช้หลายโปรแกรมพร้อมกัน

การเรียนและทำงานบนคอมพิวเตอร์มักต้องเปิดหลายโปรแกรม เช่น เว็บเบราว์เซอร์สำหรับค้นข้อมูล โปรแกรมเขียนโค้ด และโปรแกรมสื่อสาร แต่ละโปรแกรมอาจมีหลายโปรเซสที่ใช้ RAM ร่วมกับโปรเซสอื่นของระบบ เมื่อความต้องการหน่วยความจำเพิ่มขึ้น พื้นที่ที่พร้อมรองรับงานใหม่อาจลดลง

ปัญหาของผู้ใช้จึงมีมากกว่าการเห็นตัวเลข RAM สูง ผู้ใช้อาจไม่ทราบว่าแอปใดใช้หน่วยความจำมาก แอปใดเพิ่มการใช้ RAM อย่างต่อเนื่อง หรือหลังดำเนินการ Optimize แล้วเครื่องมีหน่วยความจำพร้อมใช้งานเพิ่มขึ้นจริงเท่าใด

การใช้ RAM สูงเพียงอย่างเดียวไม่ได้อธิบายสาเหตุของความช้าทั้งหมด การวิเคราะห์ต้องพิจารณาพฤติกรรมของงานร่วมด้วย โครงการจึงเริ่มจากการมองเห็นข้อมูล ก่อนให้ผู้ใช้เลือกดำเนินการและตรวจผล

### 2.2 บริบทเรื่องต้นทุน RAM

การอัปเกรด RAM เป็นทางเลือกในการเพิ่มความจุ แต่มีค่าใช้จ่ายและข้อจำกัดของอุปกรณ์ จึงเกิดคำถามว่า ก่อนซื้อฮาร์ดแวร์เพิ่ม ผู้ใช้เข้าใจการใช้ทรัพยากรของเครื่องที่มีอยู่แล้วมากเพียงใด

รายงาน TrendForce วันที่ 30 กันยายน 2026 คาดการณ์ว่าราคา Conventional DRAM แบบสัญญาในไตรมาส 4 ปี 2026 จะเพิ่มขึ้น 10-15% เมื่อเทียบกับไตรมาสก่อน ข้อมูลนี้สะท้อนแรงกดดันด้านต้นทุนในตลาดอุตสาหกรรม และยังเป็นการคาดการณ์ ไม่ใช่อัตราเพิ่มของราคา RAM ขายปลีกในประเทศไทย [TrendForce: แนวโน้มราคา DRAM ไตรมาส 4 ปี 2026](https://www.trendforce.com/presscenter/news/20260930-13258.html)

ประเด็นที่โครงการนำมาใช้คือความคุ้มค่าในการใช้ทรัพยากรที่มีอยู่ ผู้ใช้ควรมีข้อมูลประกอบการตัดสินใจว่า การปรับพฤติกรรมการใช้งานและการจัดการหน่วยความจำช่วยได้เพียงใด และเมื่อใดที่ความต้องการของงานมากกว่าความจุที่เครื่องรองรับ

### 2.3 ประเด็นเปิดการนำเสนอ

> เมื่อการเพิ่ม RAM มีค่าใช้จ่าย ก่อนตัดสินใจอัปเกรด เรารู้หรือยังว่า RAM ที่มีอยู่ถูกใช้ไปกับอะไร และมีส่วนใดที่สามารถคืนกลับมาใช้งานได้?

Thrashing Mitigator พัฒนาจากคำถามนี้ โดยให้ผู้ใช้ดูข้อมูลจริง วิเคราะห์การเปลี่ยนแปลงรายแอป และตรวจผลของการ Optimize แทนการพิจารณาเพียงตัวเลขก่อนกดปุ่ม

## 3. วัตถุประสงค์และขอบเขต

### 3.1 วัตถุประสงค์

- แสดง Total RAM, In use และ Available จากข้อมูลสดที่สอดคล้องกัน
- ช่วยให้ผู้ใช้ระบุแอปที่ใช้ RAM มากและแอปที่ RAM เพิ่มขึ้นในช่วงเวลาที่เลือก
- เรียกใช้กลไกจัดการหน่วยความจำของ Windows ผ่านโหมด Standard, Deep และ Maximum
- แสดงผลก่อนและหลัง Optimize พร้อมระยะเวลาและรายละเอียดขั้นตอน
- ให้ผู้ใช้กำหนด Auto Optimize ตามเวลา หรือเกณฑ์การใช้ RAM ได้
- เชื่อมความรู้การจัดการหน่วยความจำในบทเรียนเข้ากับระบบที่ใช้งานได้จริง

### 3.2 ขอบเขตของระบบปัจจุบัน

ระบบเป็นแอปสำหรับ Windows มีชุดแจกแบบ Portable สำหรับ Windows 10/11 x64 และรองรับภาษาไทยกับภาษาอังกฤษ รวมถึงธีม Light และ Dark ข้อมูลประวัติอยู่ในเครื่องของผู้ใช้

แอปอ่านข้อมูลและเรียกใช้บริการของ Windows จากระดับโปรแกรมทั่วไป Windows ยังคงรับผิดชอบการจัดสรรหน่วยความจำ การแปลที่อยู่ และการเลือกจัดการหน้าหน่วยความจำภายในระบบ

แอปไม่มีบริการที่ทำงานต่อหลังผู้ใช้ Exit การติดตามและ Auto ทำงานต่อได้ขณะซ่อนหน้าต่างไว้ใน Tray และหยุดเมื่อออกจากโปรแกรมจริง

### 4.1 Main Memory เป็นทรัพยากรที่หลายโปรเซสต้องใช้

บทเรียนอธิบายว่าระบบต้องบริหารหน่วยความจำให้หลายโปรเซสสามารถทำงานได้ โครงการทำให้แนวคิดนี้มองเห็นได้จากสถานการณ์จริง เช่น ขณะเปิดเบราว์เซอร์และโปรแกรมเขียนโค้ด ผู้ใช้เห็นการเปลี่ยนแปลงของ Available RAM และย้อนดูการใช้ RAM รายแอปได้

การที่หลายโปรเซสแบ่งใช้ RAM ของเครื่อง หมายถึงการแบ่งใช้ทรัพยากรที่มีจำกัด ส่วน Shared Pages หมายถึงหลายโปรเซสใช้ข้อมูลในหน้าหน่วยความจำทางกายภาพเดียวกัน สองแนวคิดนี้เกี่ยวข้องกันแต่มีความหมายเฉพาะต่างกัน

### 4.2 Logical Address และ Physical Address

โปรแกรมทำงานกับพื้นที่ที่อยู่ของตนเอง ขณะที่ระบบปฏิบัติการและฮาร์ดแวร์จัดการการเชื่อมไปยังหน่วยความจำจริง ความรู้ส่วนนี้ช่วยให้เข้าใจว่า จำนวนหน่วยความจำที่โปรแกรมจัดสรร กับจำนวนข้อมูลของโปรแกรมที่อยู่ใน RAM ไม่จำเป็นต้องเป็นค่าเดียวกัน

โครงการใช้ตัววัด Working Set เพื่อดูส่วนที่อยู่ใน RAM โดย Windows ทำหน้าที่แปลที่อยู่และจัดการ Page Table แอปไม่ได้สร้าง MMU หรือเปลี่ยนการแปลที่อยู่ของโปรแกรม

### 4.3 Paging และ Page Frames

Paging แบ่งพื้นที่หน่วยความจำเป็นหน่วยขนาดคงที่ เรียกหน่วยในพื้นที่เสมือนว่า Page และหน่วยในหน่วยความจำจริงว่า Frame ระบบใช้ Page Table เชื่อมความสัมพันธ์ระหว่างสองส่วนนี้

ความรู้เรื่อง Pages และ Frames ช่วยอธิบายการ Optimize ได้แม่นยำขึ้น เพราะการจัดการหน่วยความจำเกี่ยวข้องกับหน้าหน่วยความจำที่อยู่ใน RAM ผู้ใช้จึงควรเข้าใจว่าตัวเลขที่ลดลงหลัง Trim ไม่ได้หมายความว่าโปรแกรมปิดตัวหรือยกเลิกการจัดสรรหน่วยความจำทั้งหมด

ขนาด Page ที่ปรากฏในตัวอย่างบทเรียนใช้ประกอบการอธิบายเท่านั้น เอกสารนี้ไม่ใช้ตัวเลขตัวอย่างในตำราเป็นข้อกำหนดของ Windows ปัจจุบัน

### 4.4 Swapping และต้นทุนการเรียกข้อมูลกลับ

ตัวอย่าง Swapping ในบทเรียนแสดงการย้าย Process Image ระหว่างหน่วยความจำกับ Backing Store และกล่าวถึงเวลาที่ใช้ในการถ่ายโอนข้อมูล โครงการนำหลักเรื่องต้นทุนการนำข้อมูลกลับมาอธิบายการคืนหน่วยความจำ

กลไกหลักของแอปเป็น Working Set Trimming ระดับหน้าหน่วยความจำ ไม่ใช่การย้ายทั้งโปรเซสแบบภาพตัวอย่างในบทเรียน การเลือกจัดการแอปที่ยังใช้ข้อมูลอยู่จึงมีข้อแลกเปลี่ยนที่ต้องประเมินจากพฤติกรรมหลัง Optimize

### 4.5 Shared Pages และการอ่านตัวเลขรายแอป

บทเรียนอธิบายว่าหลายโปรเซสสามารถแชร์หน้าที่มีโค้ดหรือข้อมูลร่วมกันได้ ขณะที่ข้อมูลส่วนตัวของแต่ละโปรเซสยังแยกกัน โครงการใช้หลักนี้อธิบายว่าการรวมตัวเลข Working Set ทุกโปรเซสอาจนับหน้าที่แชร์ซ้ำ

ดังนั้น การดู RAM รายแอปมีประโยชน์ในการเปรียบเทียบพฤติกรรมของแอป แต่ผลรวมรายแอปไม่ควรนำไปแทนค่า In use ของเครื่องโดยตรง

### 4.6 Memory Protection และสิทธิ์ของ Windows

Memory Protection ในบทเรียนกล่าวถึงการควบคุมที่อยู่และการเข้าถึงหน่วยความจำ เช่น Valid/Invalid Bits ส่วนการอ่านหรือจัดการโปรเซสอื่นใน Windows ต้องผ่านสิทธิ์เข้าถึงโปรเซสของระบบ

สองเรื่องนี้เป็นการป้องกันคนละระดับ โครงการแสดงผลเมื่อเข้าถึงโปรเซสไม่ได้หรือไม่มีสิทธิ์ทำขั้นตอนระบบ และให้ผู้ใช้เลือกเปิดด้วย Administrator ผ่าน UAC การเปิดแบบ Administrator ก็ยังไม่รับประกันว่าจะเข้าถึงทุกโปรเซสได้

สิทธิ์ที่ `EmptyWorkingSet` ต้องใช้ประกอบด้วยสิทธิ์ Query โปรเซสและ `PROCESS_SET_QUOTA` ตามข้อกำหนดของ API [Microsoft: EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset)

## 5. ความรู้เสริมสำหรับอธิบายการทำงานจริง

Working Set และ Thrashing ในส่วนนี้เป็นความรู้เสริมสำหรับเชื่อมบทเรียนกับ Windows ไม่ปรากฏเป็นหัวข้อใน PDF สองฉบับที่ผู้จัดทำให้มา

### 5.1 Working Set

Working Set คือหน้าหน่วยความจำแบบ Pageable ของโปรเซสที่อยู่ใน RAM ขณะนั้น แอปเรียก `EmptyWorkingSet` เพื่อนำหน้าบางส่วนออกจาก Working Set เมื่อโปรแกรมใช้อีก Windows จะจัดการนำหน้ากลับมา หน้าอาจยังอยู่ใน RAM และกลับมาได้ด้วย Soft Page Fault หรือจำเป็นต้องอ่านจาก Backing Store ด้วย Hard Page Fault [Microsoft: Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)

การ Trim ไม่ได้ลบข้อมูลของผู้ใช้หรือยุติโปรเซส และไม่ได้ยกเลิกหน่วยความจำที่โปรแกรมจัดสรรทั้งหมด หากโปรแกรมต้องใช้หน้าที่นำออกบ่อย การ Trim อาจเพิ่มงานในการเรียกกลับ จึงต้องวัดผลหลังการดำเนินการและพิจารณาการตอบสนองของโปรแกรมร่วมด้วย

### 5.2 Thrashing และชื่อโครงการ

Thrashing เกิดเมื่อชุดหน้าหน่วยความจำที่งานกำลังใช้งานต้องการพื้นที่มากกว่า RAM ที่รองรับได้ จนระบบต้องนำหน้าออกและเรียกกลับถี่มาก เสียเวลาไปกับการเคลื่อนย้ายหน้าหน่วยความจำและกระทบการทำงานจริง การใช้ RAM สูงหรือ Page Faults ที่เกิดตามปกติเพียงอย่างเดียวไม่ยืนยันภาวะนี้ [Operating Systems: Three Easy Pieces, Chapter 22, Section 22.11](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-beyondphys-policy.pdf)

ชื่อ Thrashing Mitigator สื่อเป้าหมายในการช่วยรับมือกับภาระหน่วยความจำ ระบบปัจจุบันติดตาม RAM และดำเนินการคืนหน่วยความจำ แต่ยังไม่มีข้อมูล Page Faults และการตอบสนองของงานเพียงพอที่จะยืนยันว่าลด Thrashing ได้จริง

เกณฑ์ Warning ที่ 75% และ High RAM usage ที่ 85% เป็นเกณฑ์แสดงสถานะของแอป ผู้ใช้ต้องมีหลักฐานเพิ่มเติมก่อนสรุปว่าระบบเกิด Thrashing

## 6. ความสามารถของแอป

### 6.1 Overview: ดูสถานะปัจจุบันและ Optimize

หน้า Overview แสดง Total RAM, In use และ Available พร้อมกราฟประวัติ RAM ล่าสุด 60 ตัวอย่าง แอปอ่านข้อมูลทุก 2 วินาที จึงแสดงช่วงเวลาประมาณ 2 นาทีเมื่อมีข้อมูลต่อเนื่อง

ตัวเลข การแสดงสัดส่วน และสถานะใช้ Snapshot เดียวกัน ลดความสับสนจากค่าที่อ่านคนละเวลา ผู้ใช้เลือก Standard, Deep หรือ Maximum ได้ โดยโหมดเริ่มต้นคือ Maximum

ระหว่าง Optimize แอปแสดงขั้นตอนและป้องกันการเริ่มงานซ้ำ ผู้ใช้ยังดู RAM สดและเปลี่ยนธีมได้ เมื่อจบงาน ผลลัพธ์คงอยู่จนเริ่มรอบใหม่ มีป๊อปอัปขนาดเล็กช่วยให้ผู้ใช้ไปดูรายละเอียดด้านล่าง และปุ่มเริ่มงานกลับมาหลังช่วงรอ 3 วินาที

### 6.2 Auto: กำหนดเงื่อนไขการทำงาน

หน้า Auto ให้ผู้ใช้ตั้งการ Optimize ตามช่วงเวลา ตามเกณฑ์การใช้ RAM หรือเปิดทั้งสองเงื่อนไข เมื่อเปิดทั้งสองอย่าง เงื่อนไขใดเงื่อนไขหนึ่งสามารถเริ่มงานได้ และหากเกิดพร้อมกันจะเริ่มเพียงงานเดียว

เงื่อนไข RAM ต้องมีค่าตั้งแต่เกณฑ์ขึ้นไปต่อเนื่องตามเวลาที่กำหนดก่อนเริ่มงาน ส่วน Cooldown กำหนดระยะพักระหว่างรอบ ช่วยป้องกันการรันติดกันจากความผันผวนระยะสั้น ทั้งงาน Manual และ Auto ใช้ระบบป้องกันงานซ้อนร่วมกัน

ค่าตั้งต้นของ Profile ใหม่มีดังนี้

| การตั้งค่า | ค่าเริ่มต้น |
| --- | --- |
| Auto Optimize | ปิด |
| เงื่อนไขเวลา | เปิดไว้ในแบบฟอร์ม ช่วงเวลา 3 นาที |
| เงื่อนไข RAM | เปิดไว้ในแบบฟอร์ม เกณฑ์ 75% |
| ระยะที่ RAM ต้องมีค่าตั้งแต่เกณฑ์ขึ้นไปต่อเนื่อง | 10 วินาที |
| Cooldown | 3 นาที |
| โหมดสำหรับ Auto | Maximum |
| Start with Windows | ปิด |

การมีค่าเงื่อนไขในแบบฟอร์มยังไม่ทำให้ Auto เริ่มเอง ผู้ใช้ต้องบันทึกและเปิด Auto ก่อน ระบบใช้กฎที่ผู้ใช้กำหนด ไม่ใช้ AI ในการตัดสินใจ และยังข้ามขั้นตอนระบบที่ไม่มีสิทธิ์เหมือนการ Optimize แบบ Manual

### 6.3 Insights: เข้าใจการเปลี่ยนแปลงรายแอป

หน้า Insights เก็บการใช้ RAM รายแอปประมาณทุก 6 วินาทีและแสดงกราฟย้อนหลังสูงสุด 24 ชั่วโมง ข้อมูลยังอยู่หลังเปิดโปรแกรมใหม่ โดยมีเฉพาะช่วงที่แอปติดตามจริง

การ์ด Apps gaining RAM จัดอันดับตามการเพิ่มขึ้นระหว่างค่าต้นและปลายที่วัดได้ ส่วน View all apps สามารถเรียงตาม RAM usage เพื่อดูแอปที่ใช้ RAM มากที่สุดได้ สองอันดับตอบคนละคำถาม

ตัวอย่างเชิงอธิบาย: แอป A ใช้ RAM 1.5 GB คงที่ ขณะที่แอป B เพิ่มจาก 300 MB เป็น 700 MB แอป A อาจอยู่อันดับสูงเมื่อเรียง RAM usage แต่แอป B มีการเพิ่มขึ้น 400 MB และอาจอยู่อันดับสูงเมื่อเรียง RAM growth ตัวเลขตัวอย่างนี้ใช้สอนความต่างของอันดับ ไม่ใช่ผลทดสอบโครงการ

Insights ใช้คำอธิบายไฟล์โปรแกรมช่วยแสดงชื่อที่ผู้ใช้รู้จัก เช่น Google Chrome และ Visual Studio Code พร้อมชื่อ `.exe` ในรายละเอียด หากยืนยันชื่อไม่ได้ ระบบระบุข้อจำกัดแทนการเดาจาก PID

ประวัติ 30 นาทีล่าสุดเก็บรายละเอียด ส่วนที่เก่ากว่าสรุปเป็นรายหนึ่งนาทีพร้อมค่าสูงสุดและต่ำสุด กราฟเว้นช่องเมื่อปิดแอป พักติดตาม Sleep หรืออ่านค่าไม่ได้ และแจ้งจำนวนโปรเซสที่อ่านข้อมูลไม่ได้

เหตุการณ์การใช้ RAM เพิ่มขึ้นแสดงใน Insights และจุดแจ้งบนเมนูโดยไม่เด้งรบกวน ตัวเลขที่เพิ่มขึ้นเป็นพฤติกรรมที่วัดได้ ยังไม่ใช่คำวินิจฉัยว่าแอปมี Memory Leak

### 6.4 Settings และการใช้งานต่อเนื่อง

ผู้ใช้เปลี่ยนภาษาไทย/อังกฤษ ธีม Light/Dark และปิด Animation ได้ หน้า Settings ยังมีการจัดการข้อมูลประวัติและการตั้งค่าที่เกี่ยวข้อง

การกดปุ่มปิดหน้าต่างซ่อนแอปใน Tray เพื่อให้ Monitoring และ Auto ที่เปิดไว้ทำงานต่อ ผู้ใช้เลือก Exit จาก Tray เมื่อต้องการหยุดจริง หากมีงาน Optimize อยู่ แอปรอให้งานจบก่อนทำลาย Thread

ข้อมูลประวัติ Insights เก็บใน SQLite ภายใต้ `%LOCALAPPDATA%\ThrashingMitigatorRedesign` และไม่ส่งขึ้น Cloud การบันทึกตามรอบและการ Flush เมื่อ Exit ช่วยรักษาประวัติ แต่การปิดผิดปกติอาจทำให้ข้อมูล Batch ล่าสุดไม่ครบ

## 7. หลักการของโหมด Optimize

### 7.1 เปรียบเทียบแต่ละโหมด

| โหมด | แนวทางหลัก | การเลือกโปรเซส | ขั้นตอนระดับระบบ | ข้อแลกเปลี่ยน |
| --- | --- | --- | --- | --- |
| Standard | Trim กลุ่มแอปเบื้องหลังที่เข้าเกณฑ์ว่าง | ประเมิน CPU, Disk I/O และการเพิ่ม Working Set ยกเว้นกลุ่มแอป Foreground | ไม่มีขั้นตอนระบบเพิ่มเติม | พยายามลดการแตะแอปที่กำลังใช้งาน ผลขึ้นกับแอปที่เข้าเกณฑ์ |
| Deep | ทำ Standard แล้วเพิ่มขั้นตอนระบบ | ใช้การเลือกแบบ Standard | File Cache, Standby Purge และ Combine Identical Pages | ต้องมีสิทธิ์สำหรับขั้นตอนระบบ ผลอาจเกิดเพียงบางส่วน |
| Maximum | ดำเนินการครอบคลุมมากขึ้นและวัดหลังรอให้นิ่ง | Trim โปรเซสที่เข้าเกณฑ์รวมถึง Foreground โดยยังมีรายการยกเว้น | Page Combining, File Cache, Modified Pages และ Standby | อาจกระทบการเรียกข้อมูลกลับของแอปที่กำลังใช้งาน และผลอาจไม่คงอยู่ |

### 7.2 Standard

Standard อ่านข้อมูลโปรเซสและจัดกลุ่มจากความสัมพันธ์ Parent/Child เพื่อพิจารณาแอปที่มีหลายโปรเซสร่วมกัน ระบบตรวจว่าโปรเซสมีการใช้ CPU, Disk I/O หรือ Working Set เพิ่มขึ้นมากเพียงใด แล้วเลือกกลุ่มที่เข้าเกณฑ์สำหรับ Trim

ระบบยกเว้นกลุ่มโปรเซสของหน้าต่าง Foreground รวมถึงตัวแอปเองและโปรเซสที่กำหนดยกเว้น เมื่อเลือกเป้าหมายแล้วจะเรียก `EmptyWorkingSet` และบันทึกผลแต่ละโปรเซส การคืนหน่วยความจำมากหรือน้อยขึ้นกับหน้าที่คืนได้และการกลับมาใช้งานระหว่างวัด

ระบบ Standard มีข้อมูลประวัติการคืนและการกลับมาใช้ RAM ช่วยปรับลำดับการเลือกเป้าหมาย ลักษณะนี้เป็นกฎและคะแนนจากผลก่อนหน้า ยังไม่มีโมเดล Machine Learning

### 7.3 Deep

Deep เริ่มด้วย Standard แล้วพยายามดำเนินการ File Cache, Purge Standby และ Combine Identical Pages ผลของแต่ละขั้นตอนแยกกัน และต้องผ่านการตรวจสิทธิ์ที่เกี่ยวข้อง

Combine Identical Pages เป็นการร้องขอให้ Windows รวมหน้าที่มีเนื้อหาเหมือนกันตามกลไกของระบบ ต่างจาก Compaction ในบทเรียนที่ย้ายตำแหน่งเพื่อรวมพื้นที่ว่าง และต่างจากการบีบอัดข้อมูลในหน่วยความจำ

การ Purge Standby อาจทำให้หน้าที่อยู่ในสถานะ Free เพิ่มขึ้น แต่ Standby เป็นส่วนที่นำกลับมาใช้ได้อยู่แล้ว จึงต้องอ่าน Available ควบคู่กับ Free [Microsoft: PhysicalAvailable](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information)

### 7.4 Maximum

Maximum ดำเนินการตามลำดับในโค้ดปัจจุบันดังนี้

1. พยายาม Combine Identical Pages ขณะที่ข้อมูลยังอยู่ใน RAM
2. Trim โปรเซสที่เข้าเกณฑ์ โดยไม่ใช้ตัวกรองว่างและ Foreground แบบ Standard
3. พยายามจัดการ System File Cache
4. พยายามให้ระบบเขียน Modified Pages ไปยัง Backing Store
5. พยายาม Purge Standby
6. รอให้ค่า Available เปลี่ยนแปลงน้อยลง แล้วบันทึกผล

โหมดนี้ยังยกเว้นตัวเอง โปรเซสที่กำหนดยกเว้น และรายการที่เข้าถึงไม่ได้ ขั้นตอน Trim มีงบเวลาและจำกัดจำนวนรอบเพื่อหลีกเลี่ยงการ Trim แอปเดิมซ้ำถี่เกินไป

การเลือก Maximum เป็นค่าเริ่มต้นเป็นการตั้งค่าของผลิตภัณฑ์ ผู้ใช้ยังต้องพิจารณาผลกับงานของตนเอง หลักฐานปัจจุบันยังไม่รองรับข้อสรุปว่า Maximum ให้ผลดีที่สุดทุกครั้ง

### 8.2 การแบ่งความรับผิดชอบ

ส่วนแสดงผลรับข้อมูลผ่าน Qt Properties และ Signals จาก Backend ตัวควบคุมหน่วยความจำมีหน้าที่เผยแพร่ Snapshot, History, Mode, Busy, Progress และผล Optimize ขณะที่โมดูล Optimize ทำงานกับโปรเซสและ Windows API

งาน Optimize ใช้ Worker ใน QThread เพื่อให้ส่วนแสดงผลยังรับการใช้งานและอ่านข้อมูลสดได้ การติดตามรายโปรเซสของ Insights ใช้งานเบื้องหลังแยกกัน ส่วน Auto ตรวจเงื่อนไขจาก Snapshot RAM เดียวกับ Overview

### 8.3 ลำดับการทำงานหนึ่งรอบ

1. Monitoring อ่าน RAM รวมและส่ง Snapshot ให้ส่วนแสดงผล
2. ผู้ใช้กด Optimize หรือ Auto ตรวจพบเงื่อนไขที่พร้อมทำงาน
3. ตัวควบคุมตรวจว่าไม่มีงานซ้อน แล้วเตรียมสถานะและ Worker
4. Worker เรียกโมดูลของโหมดที่เลือก โมดูลอ่านค่าก่อนดำเนินการและส่งความคืบหน้ากลับมา
5. Backend บันทึกโปรเซสและขั้นตอนที่ทำสำเร็จหรือไม่สำเร็จ พร้อมค่าหน่วยความจำหลังดำเนินการ
6. ส่วนแสดงผลนำเสนอ Before, After, Change และ Duration รวมถึง Settling เมื่อมีข้อมูล
7. ระบบคืนปุ่มเริ่มงานหลังช่วงรอ และติดตาม RAM ต่อ

แนวทางนี้แยกการอ่านข้อมูล การดำเนินการ และการแสดงผลออกจากกัน ทำให้ตรวจสอบผลและจัดการข้อผิดพลาดได้เป็นส่วน ๆ

## 9. ตัวชี้วัดและการแปลผล

### 9.1 ความหมายของตัวเลข

| ตัวชี้วัด | ความหมายที่ใช้ในโครงการ | การแปลผล |
| --- | --- | --- |
| Total RAM | หน่วยความจำทางกายภาพที่ระบบรายงานให้ใช้งาน | ความจุส่วนนี้ไม่ได้เพิ่มจากการ Optimize |
| Available | หน่วยความจำที่ระบบพร้อมนำกลับมาใช้ | ใช้เป็นค่าหลักในการดูว่าพื้นที่พร้อมใช้งานเปลี่ยนเท่าใด |
| In use | แอปคำนวณ `Total - Available` | ดูสถานะการใช้ RAM ตามนิยามของแอป ไม่ใช่ผลรวม Working Set |
| RAM usage % | `(Total - Available) / Total × 100` เมื่อ Total มากกว่า 0 | ใช้แสดงสถานะและตรวจเงื่อนไข Auto |
| Working Set | ส่วนของหน่วยความจำโปรเซสที่อยู่ใน RAM ตามตัววัดที่อ่าน | ใช้ดูพฤติกรรมรายแอปและผล Trim |
| Free change | การเปลี่ยนแปลงของ Free + Zero Page Lists ที่ Backend อ่านได้ | ต้องพิจารณาคู่กับ Available และขอบเขตเวลาที่วัด |
| Available change | Available หลังดำเนินการ ลบ Available ก่อนเริ่ม | อาจเป็นบวก ศูนย์ หรือลบได้ |
| After settling | ค่า Available หลังขั้นตอนรอให้ค่าผันผวนน้อยลง | เป็นการสังเกตช่วงสั้นหลังงาน ไม่ใช่ผลถาวร |
| Duration | เวลาที่โมดูลรายงานสำหรับงาน Optimize | อาจรวมการ Scan และ Settling ขึ้นกับโหมด |

Available ของ Windows รวม Standby, Free และ Zero Lists ซึ่งระบบพร้อมนำกลับมาใช้ได้ จึงมีความหมายกว้างกว่า Free ที่แอปอ่านแยกจาก Memory Lists [Microsoft: PERFORMANCE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information)

ค่ารายโปรเซสของ Insights เป็น WorkingSetSize ซึ่งอาจรวม Shared Pages ส่วนตัวเลขใน Task Manager อาจใช้นิยาม การจัดกลุ่ม และเวลาอ่านต่างกัน โครงการจึงไม่อ้างว่าตัวเลขรายแอปต้องตรงกับ Task Manager ทุกจุด

### 9.2 สูตรสำหรับรายงานผล

```text
Available change = Available หลังดำเนินการ - Available ก่อนเริ่ม
Free change = Free หลังช่วงที่วัด - Free ก่อนช่วงที่วัด
RAM growth รายแอป = RAM ที่ปลายช่วง - RAM ที่ต้นช่วงซึ่งอ่านได้
```

ถ้า Available change เป็นบวก หมายถึงช่วงที่วัดมีหน่วยความจำพร้อมใช้งานเพิ่มขึ้น ถ้าเป็นศูนย์หมายถึงไม่มีการเปลี่ยนแปลงที่แสดงได้ และถ้าเป็นลบหมายถึงหน่วยความจำพร้อมใช้งานลดลงในช่วงนั้น ทั้งสามกรณีต้องรายงานตามค่าจริง

Working Set ที่ลดลงรวมเป็นตัววัดการเปลี่ยนแปลงรายโปรเซส การนำค่านี้ไปใช้แทน Available change จะทำให้ตีความผลผิด เพราะหน่วยความจำรวมของเครื่องยังเปลี่ยนตามภาระงานอื่นและสถานะหน้าหน่วยความจำด้วย

### 9.3 การอ่านผลหลัง Settling

Maximum เก็บตัวอย่าง Available ระหว่างรอ โดยจบช่วงรอเมื่อค่า 3 ตัวอย่างล่าสุดต่างกันไม่เกิน 25 MB หรือถึงเวลาสูงสุด 12 วินาที แล้วใช้ค่ากลางของตัวอย่างช่วงท้ายเป็นค่าหลัง Settling

ในโค้ดปัจจุบัน ค่าหลังจบงานของ Maximum ก็อ่านหลังขั้นตอนรอนี้เช่นกัน จึงเรียกข้อมูลสองชุดว่า “เมื่อจบงาน” และ “หลังรอให้นิ่ง” โดยไม่ตีความว่าเป็นการเปรียบเทียบค่าทันทีที่เกิดขึ้นก่อน Settling กับค่าหลัง Settling

### 9.4 หน่วยที่ใช้

ตัวเลขในรายงานภายในหาร Bytes ด้วย `1,048,576` และแสดงป้าย MB ตามแอป ซึ่งตรงกับหน่วย MiB ในระบบฐานสอง เอกสารนี้คงป้าย MB เพื่อให้ตรงกับรายงานต้นทาง หากนำไปทำกราฟควรใช้หน่วยเดียวกันทั้งชุด และระบุวิธีแปลงไว้เมื่อเปรียบเทียบกับแหล่งอื่น

## 10. ผลทดลองจริงที่มีหลักฐาน

### 10.1 ที่มาของข้อมูล

ข้อมูลส่วนนี้มาจากรายงาน `real_optimization.json` ซึ่งระบุ `realWindowsOptimization: true` เก็บในสำเนาโครงการก่อนจัดโครงสร้าง ไฟล์รายงานมีเวลาแก้ไขวันที่ 12 ตุลาคม 2026 เวลา 14:46:52 เวลานี้เป็นเวลาไฟล์ ไม่ใช่เวลาเริ่ม Optimize ของแต่ละรอบ

เครื่องทดสอบรายงาน Total RAM ประมาณ 16,107.9 MB ตามหน่วยที่อธิบายในหัวข้อ 9.4 ตารางคงความละเอียดของตัวเลขจากรายงานจริง และใช้ผลที่บันทึกไว้โดยไม่ได้สร้างผล Optimize รอบใหม่เพื่อเอกสารนี้

### 10.2 ค่าที่บันทึกได้

| โหมด | Available ก่อน (MB) | Available หลัง (MB) | เปลี่ยนแปลง (MB) | ระยะเวลา (วินาที) | โปรเซส Trim สำเร็จ | ขั้นตอนระบบสำเร็จ |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Standard | 1,359.4 | 1,397.4 | +38.0 | 9.72 | 8 | ไม่มีขั้นตอนระบบ |
| Deep | 1,324.9 | 1,074.6 | -250.3 | 5.56 | 2 | 0 จาก 3 |
| Maximum | 1,214.2 | 1,201.8 | -12.4 | 17.09 | 0 | 0 จาก 4 |

Maximum มี Available หลัง Settling 1,201.8 MB และการเปลี่ยนแปลง -12.4 MB ตรงกับค่าหลังงานในรายงานชุดนี้ Deep และ Maximum บันทึกว่าไม่ได้เปิดด้วยสิทธิ์ Administrator และขั้นตอนระบบไม่สำเร็จเพราะสิทธิ์ไม่พอ ส่วน Standard ไม่มีช่องยืนยันสถานะ Administrator จึงไม่เติมข้อมูลโดยคาดเดา

### 10.3 สิ่งที่เรียนรู้จากผลจริง

**Working Set ที่ลดลงกับ Available ที่เพิ่มขึ้นต่างกัน**

Standard รายงานการลด Working Set รวม 518.3 MB จากโปรเซสที่ Trim สำเร็จ แต่ Available เพิ่ม 38.0 MB ตัวอย่างนี้แสดงความสำคัญของการเลือกตัววัดให้ตรงกับคำถาม หากต้องการรู้ว่ามี RAM พร้อมใช้งานเพิ่มเท่าใด ควรใช้ Available change

**สิทธิ์มีผลต่อขั้นตอนที่ดำเนินการได้**

Deep และ Maximum ทำขั้นตอนระบบสำเร็จ 0 จาก 3 และ 0 จาก 4 ตามลำดับ การรายงานแยกขั้นตอนทำให้ผู้ใช้ทราบว่ารอบนั้นทำงานได้เพียงใด และช่วยตรวจหาสาเหตุของผลที่ต่างจากที่คาด

**Available RAM ของเครื่องอาจลดลงในช่วงที่ Optimize ทำงาน**

Deep และ Maximum มี Available change ติดลบ ภาระงานอื่นอาจใช้ RAM เพิ่มขึ้นระหว่างวัด หรือโปรเซสอาจเรียกข้อมูลกลับมา ข้อมูลชุดนี้ยังแยกสาเหตุแต่ละส่วนไม่ได้ จึงสรุปเพียงค่าที่สังเกตได้ ไม่ระบุว่า Optimize เป็นสาเหตุของการลดลงทั้งหมด

**Monitoring ยังทำงานระหว่าง Optimize**

รายงานทั้งสามรอบยืนยันว่า Monitoring เป็น Live และมีตัวอย่างสดระหว่างงาน 7, 5 และ 11 ตัวอย่างตามลำดับ เป็นหลักฐานว่าโครงสร้างงานเบื้องหลังยังส่งข้อมูลให้ระบบติดตามได้ระหว่างดำเนินการ

### 10.4 ข้อจำกัดของการทดลองชุดนี้

แต่ละโหมดเริ่มจาก Available ต่างกัน ไม่มีหลักฐานว่าควบคุมภาระงานให้เหมือนกัน และ Deep/Maximum มีสิทธิ์ไม่ครบ ผลชุดนี้จึงเหมาะสำหรับอธิบายการวัด การรายงานข้อจำกัด และความต่างของตัวชี้วัด

ชุดนี้เป็นการสังเกตครั้งเดียวต่อโหมด ไม่ใช้จัดอันดับว่า Standard ดีกว่า Deep หรือ Maximum และไม่มีข้อมูลเพียงพอที่จะสรุปผลด้านความเร็ว การประหยัดเงิน หรือผลของการใช้งานระยะยาว

Free change ของ Deep ในรายงานวัดเฉพาะช่วงขั้นตอนระบบหลัง Standard ส่วนของ Maximum วัดก่อนและหลังงานเต็มรอบ เอกสารจึงไม่นำ Free change ของสองโหมดมาเปรียบเทียบเป็นกราฟเดียวกัน

บางกรณีใช้ข้อมูลและผล Optimize จำลองเพื่อทำให้เงื่อนไขทดสอบเกิดซ้ำได้ ข้อมูลจำลองอยู่ใน Tests ส่วนหน้าใช้งานจริงใช้ข้อมูล Live หลักฐานการทดสอบเหล่านี้ยืนยันพฤติกรรมของระบบที่ตรวจ และแยกจากการทดลองประสิทธิภาพของเครื่อง

## 12. คุณค่าของโครงการและข้อจำกัด

### 12.1 คุณค่าที่นำเสนอได้จากระบบปัจจุบัน

โครงการช่วยให้ผู้ใช้เห็นสถานะ RAM และติดตามแอปที่มีการเปลี่ยนแปลงได้จากหน้าจอเดียว ผู้ใช้ย้อนดูข้อมูลหลังเปิดโปรแกรมใหม่ และเลือก Optimize หรือกำหนดกฎ Auto ตามความต้องการได้

การแสดงค่าก่อนและหลัง พร้อมผลแต่ละขั้นตอน ช่วยให้การ Optimize มีหลักฐานตรวจสอบ ผู้ใช้เห็นได้ทั้งกรณีที่ Available เพิ่มขึ้น ไม่เพิ่มขึ้น และกรณีทำงานบางส่วนเพราะสิทธิ์จำกัด

สำหรับการเรียน โครงการทำให้ Pages, หน่วยความจำจริง, การใช้ร่วมกันของหลายโปรเซส และต้นทุนการเรียกข้อมูลกลับ เชื่อมกับสิ่งที่พบในเครื่องจริงได้ ช่วยให้เข้าใจว่าการเลือกตัววัดมีผลต่อข้อสรุปอย่างไร

### 12.2 ข้อจำกัดที่ต้องอธิบาย

- Optimize ไม่เพิ่มความจุ RAM ทางกายภาพ และไม่ได้แก้การจัดสรรหน่วยความจำของโปรแกรมต้นเหตุ
- การลด Working Set อาจอยู่เพียงช่วงสั้นเมื่อโปรแกรมเรียกข้อมูลกลับ
- โปรแกรมที่ใช้ข้อมูลอยู่สามารถมีต้นทุนเพิ่มหลัง Trim ต้องตรวจผลด้านการตอบสนองเพิ่มเติม
- ค่า Available เปลี่ยนตามกิจกรรมทั้งเครื่อง จึงต้องควบคุมภาระงานก่อนสรุปเหตุและผล
- การใช้ RAM เพิ่มขึ้นยังไม่ยืนยัน Memory Leak และเกณฑ์ RAM สูงยังไม่ยืนยัน Thrashing
- โปรเซสที่ถูกป้องกันหรือสิทธิ์ไม่พออาจอ่านหรือจัดการไม่ได้
- ประวัติครอบคลุมช่วงที่แอปทำงานจริง ไม่มีข้อมูลจากช่วงหลัง Exit
- แอปเองใช้ CPU, RAM และพื้นที่เก็บประวัติ จึงควรวัดต้นทุนของการติดตามร่วมกับประโยชน์

### 12.3 การตัดสินใจเรื่องอัปเกรด

ข้อมูลจากแอปช่วยประกอบการตัดสินใจว่า ผู้ใช้ควรลดงานที่ไม่จำเป็น ตรวจแอปที่มีพฤติกรรมเพิ่ม RAM หรือปรับการใช้งานอย่างไร หากงานที่จำเป็นต้องทำพร้อมกันยังต้องการหน่วยความจำมากกว่าที่เครื่องรองรับ การเพิ่มความจุ RAM ยังคงเป็นทางเลือกที่ต้องประเมินตามงานและอุปกรณ์

โครงการยังไม่มีหลักฐานคำนวณจำนวนเงินที่ประหยัดได้หรือระยะเวลาที่เลื่อนการอัปเกรด จึงนำเสนอความคุ้มค่าในฐานะข้อมูลช่วยตัดสินใจและการใช้ทรัพยากรที่มีอย่างเข้าใจ

## 13. แนวทางพัฒนาและการทดลองเพิ่มเติม

หัวข้อนี้เป็นงานในอนาคต ไม่ใช่ฟีเจอร์หรือผลสำเร็จที่มีแล้ว

### 13.1 เพิ่มตัววัดด้านประสิทธิภาพ

เก็บ Hard Page Faults, ปริมาณ Disk I/O และเวลาตอบสนองของงานที่ผู้ใช้ทำ เพื่อดูว่า Available ที่เพิ่มขึ้นสัมพันธ์กับการใช้งานดีขึ้นหรือมีต้นทุนในการเรียกข้อมูลกลับมากขึ้น

ควรวัดผลหลัง Optimize ต่อเนื่อง เช่น 30 วินาที, 1 นาที และ 5 นาที เพื่อแยกการเปลี่ยนแปลงระยะสั้นออกจากผลที่คงอยู่ โดยระบุช่วงเวลาเดียวกันสำหรับทุกโหมด

### 13.2 ทดลองเปรียบเทียบอย่างควบคุม

กำหนดภาระงานเดียวกันและสถานะสิทธิ์ให้เท่ากัน เปรียบเทียบกรณีไม่ Optimize กับ Standard, Deep และ Maximum เริ่มแต่ละรอบจากสภาพใกล้เคียงกันและทำซ้ำหลายรอบ โดยสลับลำดับโหมดเพื่อลดผลจากลำดับการทดลอง

บันทึก Available, Working Set, Disk I/O และเวลาของงานที่กำหนด พร้อมแสดงค่ากลางและความกระจาย ผลที่ไม่มี RAM เพิ่มต้องอยู่ในข้อมูลด้วย จากนั้นจึงประเมินว่าโหมดใดเหมาะกับภาระงานแต่ละประเภท

### 13.3 ประเมินต้นทุนของแอป

เปรียบเทียบการใช้ CPU/RAM ของเครื่องเมื่อไม่เปิดแอป เมื่อเปิด Overview เมื่อเปิด Insights และเมื่อซ่อนไว้ใน Tray เพื่อประเมินต้นทุน Monitoring แยกจากกิจกรรมของโปรแกรมอื่น

### 13.4 เพิ่มความเข้าใจจาก Insights

พัฒนาการเชื่อมเหตุการณ์กับการเปลี่ยนแปลงรายแอปให้ชัดขึ้น และเพิ่มการส่งออกรายงานสำหรับวิเคราะห์ โดยคงการระบุข้อมูลที่อ่านไม่ได้และหลีกเลี่ยงการสรุปว่า RAM growth เป็น Memory Leak โดยไม่มีหลักฐานเพิ่มเติม

## 14. บทสรุปโครงการ

Thrashing Mitigator นำความรู้การจัดการหน่วยความจำมาประยุกต์เป็นแอปที่ติดตาม RAM สด วิเคราะห์ประวัติรายแอป และเรียกใช้กลไกของ Windows พร้อมตรวจผลหลังดำเนินการ

ผลทดลองที่มีแสดงว่าการลด Working Set และการเพิ่ม Available RAM เป็นคนละตัววัด การมีระบบรายงานค่าจริงและข้อจำกัดจึงเป็นส่วนสำคัญของโครงการ เพราะช่วยให้ผู้ใช้เข้าใจว่ารอบนั้นทำอะไรได้และมีผลเท่าใด

ในบริบทที่การอัปเกรดมีค่าใช้จ่าย โครงการเสนอให้เริ่มจากความเข้าใจทรัพยากรของเครื่อง ข้อมูลที่ชัดช่วยให้ผู้ใช้ประเมินการปรับการใช้งานและความจำเป็นในการเพิ่ม RAM ได้มีเหตุผลมากขึ้น ส่วนผลด้านความเร็วและการลด Thrashing เป็นประเด็นที่ต้องพิสูจน์ต่อด้วยการทดลองควบคุม

## 15. คำถามที่อาจารย์อาจถาม

### ทำไมต้องทำแอปนี้ ทั้งที่ Windows จัดการ RAM อยู่แล้ว?

Windows ทำหน้าที่บริหารหน่วยความจำของระบบ โครงการเพิ่มส่วนที่ผู้ใช้ดูข้อมูลสด ย้อนดูประวัติรายแอป กำหนดกฎการดำเนินการ และตรวจผลของการ Optimize ได้สะดวก จุดประสงค์คือประยุกต์ความรู้ OS กับการสังเกตและการใช้งานจริง

### แอปทำให้ RAM จาก 8 GB กลายเป็น 16 GB ได้หรือไม่?

ความจุฮาร์ดแวร์คงเดิม แอปพยายามคืนหน่วยความจำบางส่วนและรายงาน Available ที่เปลี่ยนแปลง การเพิ่มความจุจริงต้องอาศัยฮาร์ดแวร์

### โครงการเกี่ยวข้องกับบทเรียนตรงไหนมากที่สุด?

เกี่ยวกับ Main Memory ที่หลายโปรเซสต้องใช้ Paging ที่ช่วยอธิบาย Pages/Frames และ Swapping ที่ชี้ให้เห็นต้นทุนการนำข้อมูลกลับมา Shared Pages ยังช่วยอธิบายข้อจำกัดของการรวมค่ารายโปรเซส ส่วนการทำงานของแอปอาศัยบริการที่ Windows จัดให้

### ทำไม Working Set ลดมาก แต่ Available เพิ่มน้อย?

ตัวเลขแรกเป็นการเปลี่ยนแปลงรายโปรเซส ส่วนตัวเลขหลังเป็นสถานะรวมของเครื่อง ผล Standard ในรายงานลด Working Set รวม 518.3 MB แต่ Available เพิ่ม 38.0 MB จึงต้องระบุนิยามและช่วงวัดก่อนสรุปผล

### ทำไมบางครั้ง Optimize แล้ว RAM พร้อมใช้งานลดลง?

ค่ารวมเปลี่ยนตามงานทั้งเครื่อง โปรเซสอาจใช้ RAM เพิ่มหรือเรียกข้อมูลกลับระหว่างวัด อีกทั้งบางขั้นตอนอาจทำไม่ได้เพราะสิทธิ์ รายงานปัจจุบันยังแยกสาเหตุทุกส่วนไม่ได้ จึงแสดงผลติดลบตามจริง

### Maximum ดีกว่า Standard เสมอหรือไม่?

Maximum ดำเนินการครอบคลุมมากขึ้นรวมถึงแอป Foreground จึงมีข้อแลกเปลี่ยนต่างจาก Standard ผลขึ้นกับงานและสิทธิ์ ชุดทดสอบที่มีไม่ได้ควบคุมสภาพให้เท่ากัน จึงยังใช้ตัดสินโหมดที่ดีที่สุดไม่ได้

### แอปใช้ FIFO หรือ LRU ในการเลือก Page หรือไม่?

แอปเลือกกลุ่มโปรเซสตามกฎที่กำหนดและเรียก Windows API ส่วนการจัดการ Page ภายในเป็นหน้าที่ Windows โครงการไม่ได้ implement อัลกอริทึม Page Replacement ของ Kernel

### Page Combining คือ Compaction หรือ Memory Compression หรือไม่?

Page Combining มุ่งรวมหน้าที่มีเนื้อหาเหมือนกัน ส่วน Compaction ในบทเรียนมุ่งรวมพื้นที่ว่างด้วยการย้ายตำแหน่ง และ Compression ลดขนาดข้อมูลด้วยการบีบอัด เป็นกลไกที่มีเป้าหมายเฉพาะต่างกัน

### ทำไมตัวเลขไม่ตรงกับ Task Manager ทุกครั้ง?

Insights ใช้ WorkingSetSize พร้อมวิธีจัดกลุ่มและเวลาอ่านของแอป การเทียบกับ Task Manager ต้องตรวจว่าใช้ตัววัด กลุ่มโปรเซส และเวลาเดียวกันหรือไม่ รวมถึงส่วน Shared Pages และรายการที่อ่านไม่ได้

### Auto ใช้ AI หรือไม่?

Auto ใช้เงื่อนไขเวลา RAM threshold, Sustained duration และ Cooldown ที่ผู้ใช้กำหนด ส่วนคะแนนประวัติใน Standard เป็นกฎปรับการเลือกเป้าหมาย โครงการยังไม่มีโมเดล AI

### ยืนยันได้หรือยังว่าลด Thrashing และทำให้เครื่องเร็วขึ้น?

หลักฐานปัจจุบันยืนยันการติดตาม การเรียก Optimize และการแสดงค่าที่วัดได้ ยังต้องเก็บ Page Faults, Disk I/O และเวลาตอบสนองภายใต้การทดลองควบคุมเพื่อประเมินผลด้านนี้

### ถ้าอาจารย์ถามว่าช่วยประหยัดเงินได้เท่าไร?

ยังไม่มีการทดลองด้านค่าใช้จ่ายที่คำนวณตัวเลขนี้ได้ สิ่งที่เสนอคือข้อมูลช่วยประเมินการใช้ทรัพยากรและความจำเป็นในการอัปเกรด ส่วนเงินที่ประหยัดหรือระยะเวลาที่เลื่อนการซื้อขึ้นกับเครื่องและงานของผู้ใช้
